# Wine 11.16 FL Studio patch verification

This is the local verification record for the initial supported build. It does
not contain or redistribute Image-Line binaries.

## Inputs

- Upstream Wine commit: `8da89f8493b21ebfbe344a54dbef0cde23c7ea59`
- Wine-Staging commit: `f1936f02ba06b5012f89f75901944e8c2d26951c`
- Installed FL Studio version: 26.1.5.5618
- `FLEngine_x64.dll` SHA-256:
  `b85d5274d643a9aad24f898e17de5b5ddf668487e9e0c6968b0e47f5a619bdd3`

## Test-first evidence

The unpatched Wine 11.16 crypt32 test executable ran 1,030 assertions after the
new fixture was added. Exactly the valid unsorted-attribute assertion failed
with `NTE_BAD_SIGNATURE`; the tampered-signature assertion passed.

After the verification-only encoder change, the same `msg` subtest ran 1,030
assertions with zero failures. The valid unsorted fixture passed and its
signature-tampered copy remained rejected.

The adjacent system-Wine baseline suites also completed with zero failures:

- rsaenh: 4,099 assertions
- WinTrust ASN: 211 assertions
- WinTrust crypt/catalog: 378 assertions
- WinTrust registration: 40 assertions
- WinTrust softpub: 254 assertions

After the complete private build, fresh `msg.ok`, `rsaenh.ok`, `asn.ok`,
`crypt.ok`, `register.ok`, and `softpub.ok` targets all exited successfully
against the full patched Wine-Staging tree.

The exported series also trial-applied without conflicts or whitespace errors to
then-current upstream Wine HEAD
`cd22bd7383ae34d3597aebf47fbb3184e19e473b`. This is portability evidence, not a
claim that the unbuilt revision is supported; the application script therefore
continues to require `ALLOW_UNTESTED_WINE=1` outside the pinned 11.16 base.

## Build and runtime evidence

The serial optimized build completed for `i386,x86_64` and installed to the
versioned private prefix. The runner reports:

```text
wine-11.16-282-gfd3bd73 (Staging)
```

The system runner remained `/usr/bin/wine`, version `wine-11.16 (Staging)`, with
the same before-and-after SHA-256:

```text
509aeb9e3b6330a9ccbfc4a762b98fe41db0a95785559f5b0c1e8fe8c6fd121a
```

The exact same pinned Image-Line DLL produced this result matrix:

| Runner/input | WinVerifyTrust | Expected result |
| --- | ---: | --- |
| System Wine, genuine DLL | `80096004` | Reproduced old failure |
| Private Wine, genuine DLL | `00000000` | Accepted |
| Private Wine, byte-tampered copy | `80096010` | Rejected |

FL Studio then launched with the private runner. Its `FL64.exe` process,
embedded WebView processes, main `FL Studio 2026` window, settings window, and
welcome window were all present; no validity-verification dialog was present.
The welcome window displayed trial mode, which is separate registration state
and was intentionally not modified by this compatibility patch.

## Workflow hardening evidence

The exact-source preparation script was rerun against fresh Wine 11.16 and
Wine-Staging 11.16 checkouts. It verified both stable patch IDs, applied the
complete series, and atomically wrote the final source provenance record.

The build workflow then reused the completed dual-architecture build only after
matching its source path, private install prefix, compiler, flags, and
`i386,x86_64` configuration. It forcibly reran all six focused test targets
before reinstalling the private runner. Negative checks confirmed that the
workflow rejects a missing provenance record, an install prefix outside the
user's home, a stale build configuration, and a pre-existing Git operation.

The local FL verifier was also rerun with strict compiler warnings. It accepted
the pinned genuine DLL with `00000000`, rejected the temporary byte-tampered DLL
with exactly `80096010`, and removed the proprietary temporary copy on exit.
